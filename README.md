# RAG-ассистент по регламентам

## Структура проекта

```
project/
├── app.py                  # FastAPI: страницы, /ask, /documents, /folders, /catalog, /plans, /employees
├── auth.py                 # Вход администратора: scrypt-хэши паролей, сессии в куке, защита от перебора
├── employees.py            # Сотрудники и персональные расписания (план + дата выхода)
├── indexing.py             # Вся логика docling -> классификация по папкам -> чанкинг -> эмбеддинги -> Qdrant
├── classifier.py           # LLM-раскладка документов по смысловым папкам + реестр папок
├── planner.py              # Конструктор плана адаптации: модель, расчёт дат, генерация, экспорт
├── index_documents.py      # CLI: разовая пакетная индексация папки data/documents
├── rag.py         # RAG-пайплайн: анализ истории диалога -> классификация -> поиск -> реранк -> генерация
├── requirements.txt
├── static/
│   ├── index.html          # Публичная страница сотрудника: чат с ассистентом
│   ├── login.html          # Форма входа администратора
│   └── admin.html          # Админка: база знаний, конструктор плана, сотрудники
└── data/                   # Специально отведённая папка для документов — ничего вручную сюда не класть, кроме файлов регламентов
    ├── documents/           # Оригиналы файлов, разложенные по смысловым папкам
    │   ├── _inbox/           # Свежезагруженные файлы до классификации
    │   └── <Тема>/           # Папки создаёт LLM по содержанию документа
    ├── processed/           # Кэш DoclingDocument в JSON — чтобы не парсить PDF/DOCX повторно
    ├── plans/               # Планы адаптации: plan.json, plan.md, schedule.json, schedule.md
    ├── stage_catalog.json   # Каталог этапов и шаблонов подэтапов для конструктора
    ├── folders.json         # Реестр смысловых папок: название + описание темы
    ├── employees.json       # Сотрудники: данные, назначенный план, дата выхода
    ├── admins.json          # Учётки администраторов: логин, соль, scrypt-хэш (открытых паролей нет)
    └── registry.json        # Реестр: какой файл когда загружен, статус индексации, число чанков, папка
```

## Страницы и доступ

| Страница | Кто | Что там |
|---|---|---|
| `/` | сотрудник, без входа | Чат с ассистентом по регламентам |
| `/login` | администратор | Форма входа |
| `/admin` | администратор, по сессии | База знаний, конструктор плана, сотрудники |

**Первый запуск.** Учётка `admin` создаётся автоматически. Пароль берётся из переменной
окружения `NEIROMASTER_ADMIN_PASSWORD`, если она задана; иначе генерируется случайный,
печатается в лог сервера и дублируется в `data/admin_initial_password.txt`.
Смените пароль в админке («Сменить пароль») и удалите этот файл.

Задать пароль заранее при запуске через systemd:

```bash
sudo systemctl set-environment NEIROMASTER_ADMIN_PASSWORD='ваш-пароль'
```

**Как устроен вход.** Пароли хранятся как scrypt-хэш с индивидуальной солью — открытых
паролей на диске нет. После входа выдаётся токен сессии в httponly-куке (JS её не читает,
`SameSite=Lax` отсекает кросс-сайтовые POST). Сессия живёт 12 часов без активности и только
в памяти процесса: перезапуск сервера = перелогин. После 10 неудачных попыток логин
блокируется на 5 минут. Смена пароля сбрасывает все сессии.

Ограничения, которые стоит помнить: одна роль (администратор), сессии не переживают
перезапуск и не шарятся между воркерами — для нескольких uvicorn-воркеров их надо вынести
в Redis. И обязательно поднимите HTTPS перед публикацией наружу: кука с токеном ходит
в открытом виде по HTTP.

Все админские ручки (`/documents`, `/folders`, `/catalog`, `/plans`, `/jobs`, `/employees`)
требуют сессии и отвечают 401 без неё. Публичные — только `/`, `/login`, `/ask` и `/session/{id}`.

Внутри `data/documents/` уже лежат два тестовых регламента для проверки:
- `reglament_ohrana_truda.docx` — общий регламент по охране труда (СИЗ, инструктажи, отпуска, режим труда)
- `instrukciya_vysota_pozhbezopasnost.pdf` — работа на высоте, пожарная и электробезопасность

## Контекст диалога (история вопросов)

Сайт запоминает последние вопросы пользователя в рамках одной открытой вкладки
браузера (`session_id` живёт в переменной страницы и сбрасывается при
перезагрузке, сама история хранится в памяти сервера). Если новый
вопрос короткий и обрывочный ("Где взять", "А сколько?") — перед поиском и
генерацией ответа `rag.py` анализирует последние до 3 вопросов из
истории и переписывает его в полный самостоятельный вопрос (например, "Где
взять экипировку для работы на высоте?"). Если вопрос уже самодостаточен —
история не используется, лишний вызов модели не тратится.

Кнопка «🔄 Новый диалог» на сайте сбрасывает историю и начинает сессию заново.

## Путь документа до готовности к нейропоиску

```
Загрузка файла (сайт или папка data/documents)
        │
        ▼
DocumentConverter (docling) — разбор PDF/DOCX/PPTX/HTML:
структура, заголовки, таблицы, страницы
        │
        ▼
DoclingDocument — кэшируется в data/processed/*.json
(повторная обработка того же файла не парсит документ заново)
        │
        ▼
HybridChunker — смысловые чанки по разделам, с учётом
токенного бюджета эмбеддинг-модели
        │
        ▼
contextualize() — к каждому чанку приклеивается путь
заголовков ("Раздел 5 / Отпуска / Доп. отпуск")
        │
        ▼
Эмбеддинг (bge-m3, 1024d) для текста чанка
        │
        ▼
Qdrant (HNSW-индекс, COSINE) — финальный формат,
готовый к нейропоиску за миллисекунды
```

## Установка (Linux-сервер)

Скопируйте папку `project/` на сервер, зайдите в неё по SSH и запустите:

```bash
chmod +x install.sh
./install.sh
```

Работает и от root, и от обычного пользователя с sudo. Скрипт ставит:
apt-пакеты → venv + `pip install -r requirements.txt` → Qdrant в Docker (`--restart unless-stopped`) → Ollama как systemd-сервис + модели → systemd-сервис `rag-app` для самого сайта.

Если что-то из этого уже установлено (Docker, Ollama) — соответствующий шаг скрипт пропустит.

**Важные моменты именно для сервера:**
- В коде Ollama ожидается на порту `8080`, а не на стандартном `11434` — скрипт переопределяет это через systemd drop-in (`OLLAMA_HOST=127.0.0.1:8080`).
- Порты Qdrant (6333/6334) и Ollama (8080) привязаны только к `127.0.0.1` — они не торчат наружу на публичный IP сервера, приложение обращается к ним через localhost. Открывать их в firewall не нужно.
- Сайт и Ollama запускаются как systemd-сервисы (`rag-app`, `ollama`), а не фоновыми процессами — переживают обрыв SSH-сессии и перезагрузку сервера.
- `qwen3:14b` (модель генерации ответа) без GPU требует **~9+ ГБ оперативной памяти** только под себя; с учётом `qwen2.5:3b` и `bge-m3` закладывайте от 16 ГБ RAM на сервер. Если сервер слабее — замените `qwen3:14b` в `rag.py` (`BIG_MODEL`) на модель поменьше.

```bash

# Сайт запускается как systemd-сервис

```

Сайт: `http://<IP-сервера>:8000` — если нужен доступ снаружи, откройте порт в firewall:
```bash
sudo ufw allow 8000/tcp
```

## Как работает загрузка через сайт

1. Пользователь перетаскивает PDF/DOCX в область загрузки на сайте.
2. `POST /documents/upload` сохраняет файл в `data/documents/_inbox/` (имя очищается от опасных символов, путь traversal исключён).
3. Сразу же вызывается `indexing.index_document()`: docling-конвертация → LLM определяет смысловую папку → файл переезжает в `data/documents/<папка>/` → чанкинг → эмбеддинги → запись в Qdrant с полем `folder` в payload.
4. Ответ сайту содержит статус, число чанков и выбранную папку; список документов и папок на странице обновляется автоматически.
5. Повторная загрузка файла с тем же именем переиндексирует его (старые чанки в Qdrant удаляются перед записью новых).
6. Кнопка «Удалить» у документа убирает и векторы из Qdrant, и сам файл, и кэш docling.

## Сортировка документов по содержанию (папки)

Папки никто не заводит вручную — их создаёт LLM. Логика в `classifier.py`:

- В `data/folders.json` лежит реестр папок: название + описание темы. При первом запуске
  туда кладётся стартовый набор из 9 тем — он задаёт модели «язык» именования, чтобы
  не плодились синонимы («ОТ», «Охрана труда», «Техника безопасности»).
- При загрузке документа малая модель получает первые ~4000 символов текста и список
  существующих папок, и возвращает JSON `{"folder", "is_new", "description", "confidence"}`.
- Если подходящей папки нет — модель придумывает новую, она регистрируется и создаётся на диске.
- Если модель недоступна или ответила мусором, документ попадает в «Без категории»:
  загрузка не должна падать из-за LLM.

Имя папки пишется в payload каждого чанка. Благодаря этому конструктор плана сначала
выбирает подходящие папки по названию и описанию, и только потом ищет чанки внутри них —
это и есть «сортировка по содержанию с помощью названия папок».

## Конструктор плана адаптации (вкладка «🗓️ Конструктор плана»)

Человек собирает расписание сообщений новому сотруднику, система генерирует тексты по документам.

**Как собирается план**

1. Этапы выбираются из каталога `data/stage_catalog.json` (8 этапов: предварительная
   адаптация, первый день, первая неделя, стажировка, проверка знаний и допуск, начало
   самостоятельной работы, интеграция, итоги). Каталог намеренно профессионально-независимый:
   специфика должности приходит из документов, а не из названий этапов. Можно добавить и свой этап.
2. У этапа задаётся длительность: часы / дни / недели / месяцы, и якорь — «до выхода на работу»
   или «от даты выхода».
3. Подэтапы берутся из шаблонов этапа (всего 62 заготовки) либо пишутся вручную. У подэтапа есть
   тип (сообщение, чек-лист, опрос, мини-тест, напоминание, системная проверка, задача человеку)
   и описание того, что должен написать бот — оно и уходит в LLM как задание.
4. Время срабатывания: день внутри этапа (1…N, где N считается из длительности) и время суток.
   Если длительность задана в часах — день не выбирается, только время.

**Как считается дата отправки**

Время хранится относительно даты выхода сотрудника, не абсолютно. Этапы с якорем
«до выхода» выстраиваются подряд так, чтобы последний их день пришёлся на день перед выходом
(смещение −1), этапы «от даты выхода» — подряд начиная с дня выхода (смещение 0). Абсолютные
дата и время получаются подстановкой `start_date`, поэтому один и тот же план переиспользуется
для любого новичка.

**Генерация автоответов**

`POST /plans/{id}/generate` запускает фоновую задачу; фронтенд тянет прогресс через
`GET /jobs/{job_id}`. По каждому подэтапу:

```
описание подэтапа + тип + темы
        │
        ▼
малая модель выбирает 1–3 смысловые папки базы знаний
        │
        ▼
векторный поиск в Qdrant с фильтром по этим папкам (6 чанков)
        │
        ▼
qwen3:14b пишет готовое сообщение сотруднику строго по фрагментам
```

Отдельный подэтап можно перегенерировать, не прогоняя весь план:
`POST /plans/{id}/messages/{message_id}/regenerate`.

**Что на выходе**

| Файл | Что это |
|---|---|
| `plan.json` | Канонический план — источник истины, из него всё считается |
| `plan.md` | Тот же план в удобном для LLM виде |
| `schedule.json` | Плоский список сообщений с временем отправки — формат под мессенджеры и самописное приложение |
| `schedule.md` | Человекочитаемая таблица этап / подэтап / дата и время / ответ |

Одно сообщение в `schedule.json`:

```json
{
  "message_id": "st1_pre_onboarding.s1_greet_intro",
  "stage":    { "id": "st1_pre_onboarding", "order": 1, "title": "Предварительная адаптация" },
  "substage": { "id": "s1_greet_intro", "order": 1, "title": "Приветствие", "kind": "message" },
  "schedule": { "anchor": "before_start", "stage_day": 1, "time": "10:00",
                "offset_days": -3, "send_at": "2026-08-29T10:00" },
  "content":  { "format": "markdown", "text": "Добрый день, [Имя]! ..." },
  "actions":  [],
  "folders_used": ["Адаптация и наставничество"],
  "sources":  [{ "source": "Положение по адаптации.pdf", "folder": "...", "page": 3, "score": 0.87 }],
  "status": "generated"
}
```

Формат специально плоский и самодостаточный: планировщику мессенджера нужны только
`send_at` (или `offset_days` + `time`, если дата выхода подставляется в момент найма),
`content.text` и `message_id` для идемпотентности. Поле `actions` зарезервировано под
кнопки и варианты ответа сотрудника.

## Сотрудники и назначение планов (вкладка «👥 Сотрудники»)

Администратор заводит сотрудника, выбирает готовый план-шаблон и дату выхода на работу.
Персональное расписание считается на лету:

```
план (относительные смещения)
      + дата выхода сотрудника        -> конкретные дата и время каждого сообщения
      + сгенерированные тексты плана  -> содержимое сообщений
      + данные сотрудника             -> подстановка [Имя], [ФИО наставника], [Должность]
```

Тексты под каждого сотрудника заново не генерируются: они зависят от документов компании,
а не от человека. Один сгенерированный план обслуживает сколько угодно новичков — меняются
только даты и плейсхолдеры. Правка плана или даты выхода сразу отражается в расписании,
пересчёт вручную не нужен.

Поля сотрудника: ФИО, должность, подразделение, контакт, наставник, руководитель,
назначенный план, дата выхода, статус (`planned` / `active` / `paused` / `done`), заметки.
Наставник и руководитель нужны не только для справки — из них подставляются плейсхолдеры
в текстах сообщений.

Если у плана ещё не сгенерированы ответы, расписание всё равно покажется: даты рассчитаны,
тексты пустые, и в интерфейсе висит предупреждение.

| Метод | Путь | Назначение |
|---|---|---|
| GET/POST | `/employees` | Список сотрудников / создание |
| GET/PUT/DELETE | `/employees/{id}` | Чтение / обновление / удаление |
| GET | `/employees/{id}/schedule` | Персональное расписание (пересчитано на дату выхода) |
| GET | `/employees/{id}/export/{schedule.md\|schedule.json}` | Скачивание персонального расписания |
